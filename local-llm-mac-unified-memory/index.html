How do you size a Mac for local inference?

Apple silicon shares memory between the CPU, GPU and applications. Size a machine for the combined workload you intend to keep open.

2026-11-22

Size a Mac for the model, its longest conversation and the applications you keep open together. Start with this planning rule: add the measured inference working set to your normal desktop usage, then keep at least 25% of that combined estimate available as headroom.

Unified memory is one shared budget

Apple silicon's CPU and GPU access the same memory pool. MLX uses that architecture so arrays can participate in CPU or GPU operations without moving between separate memory pools. A Mac advertised with 32 GB has one 32 GB pool shared by applications and the GPU.

Make the budget concrete. Suppose your chosen model and context use 12 GiB while your editor, browser, document store and system use another 6 GiB. The combined workload is 12 + 6 = 18 GiB. Adding this guide's 25% planning margin gives 18 × 1.25 = 22.5 GiB. That is an illustrative sizing exercise; replace both inputs with measurements from your workload.

Keep your units straight when checking a specification against a tool reporting bytes. One GiB is 1,073,741,824 bytes. Also distinguish capacity from speed: buying enough memory to hold a model answers whether it fits, while your own prompt and answer timings determine whether it is pleasant to use.

These are representative current Apple silicon configurations verified on Apple's specification pages on 2026-11-22. Match the memory tier to the exact chip and GPU configuration.

Use the table to find candidates after calculating the budget. Do not begin with the largest model someone has managed to load and work backward to a purchase. A useful purchase decision includes an exact artifact, context length, number of simultaneous requests and an acceptable completion time.

Storage capacity is a separate choice. Apple's specifications list SSD options separately from unified memory. Size storage for model downloads and unified memory for the running workload.

Understand the GPU memory limit

Metal exposes recommendedMaxWorkingSetSize, an estimate of the GPU resource footprint that can be allocated without affecting runtime performance. Use the value reported by your device as a performance threshold and budget separately for the rest of the system.

Runtimes also implement their own allocation policies. In the MLX Metal allocator source checked on 2026-11-22, the initial memory limit is the smaller of 1.5 times the recommended working set and 0.95 times physical memory. Written as arithmetic, limit = min(1.5 × recommended bytes, 0.95 × physical bytes). Apply this library allocation policy within the machine's physical memory budget.

For illustration, if a device reported a 24 GiB recommended set and 32 GiB physical memory, those terms would be 36 GiB and 30.4 GiB, producing a 30.4 GiB allocator limit. Your editor and operating system still need memory. Use that ceiling to diagnose allocation failures, while sizing the workload with room for your other applications.

Reducing the model, context or simultaneous sessions is the first response to memory pressure. Keep the physical capacity fixed in your worksheet when changing software limits. Keep a stable configuration that works with your desktop before experimenting with allocation overrides.

Read pressure and swap together

In Activity Monitor, open the Memory tab and record Physical Memory, Memory Used, Memory Pressure and Swap Used. Apple explains that pressure incorporates free memory, swap rate, wired memory and cached files. Swap Used reports space used on the startup disk for swapping.

A single low free-memory reading is therefore an incomplete diagnosis. Look for a pattern: pressure rises during the long conversation, swap grows, and later answers take longer. Compare the model run with an otherwise identical desktop session. That gives you a reason to change capacity rather than blaming every delay on the model.

Record the initial swap reading as well as the final value. Subtract the initial reading from the final reading to track the change during the experiment. Keep other application activity similar across comparisons.

Try it on your workload

Open your usual editor, browser and document store. Record the baseline Memory tab values. Load the exact model you intend to use, with a fixed context and one active conversation. Ask a short question, then process the longest representative document and continue until you have ten answers.

For answers one, two and ten, record first-response delay, completion time, pressure and swap. Save the outputs so you can check whether a quicker configuration simply produced a worse answer. Repeat the entire sequence with a smaller quantization or shorter context, changing only one setting.

If several agents are part of normal use, repeat with that number of requests. Keep a worksheet containing the peak combined workload and the largest acceptable delay. Use those results, plus your margin, to choose the next available memory tier.

How to decide

  • Keep the Mac you own when your real desktop and longest conversation remain responsive together.
  • Choose more unified memory when recurring useful work exceeds the combined budget or shows sustained pressure and growing swap.
  • For rare large jobs, compare renting inference before choosing a workstation-sized memory configuration.
