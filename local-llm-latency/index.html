How fast will a local model feel in chat?

Separate time to first token from the speed of the remaining answer. Long prompts can make an otherwise fast generator feel unresponsive.

2026-11-22

For an initial chat test, try illustrative targets of first visible output within three seconds and a complete short answer within fifteen. Measure both separately so you can distinguish time spent reading your document from time spent generating the answer.

Divide the wait into stages

Start a timer when your application submits the request. Mark the first visible output and the last output. Then compare those observations with the runner's reported loading, prompt-processing and generation durations. The user's experience includes work outside the model, so do not substitute an internal timing for the whole wait.

Stage Question it answers Useful change to test
Queue and application work How long before inference can proceed? Fewer simultaneous requests; less application-side preparation
Model loading Is the model already available? Separate first-use and already-loaded trials
Prompt evaluation How long to process uncached input? Shorter relevant context
Token generation How quickly does the answer grow? Smaller useful model or shorter output budget

Define both acceptance targets before tuning. Adjust the opening targets according to what the user is doing while waiting, and record which target each configuration meets.

Keep correctness in the timing sheet. The useful metric is how soon an acceptable answer arrives. A model that streams quickly but needs repeated correction can lose to a slower first response.

Read Ollama's verbose output correctly

With Ollama running and a model already downloaded, replace the name below and request timings:

ollama run YOUR_LOCAL_MODEL --verbose "Explain in three sentences why the Moon has phases."

Ollama's CLI prints timing information after the response. In the November 2026 implementation, prompt eval rate uses uncached prompt tokens divided by prompt-evaluation seconds, while eval rate uses generated tokens divided by generation seconds. It also reports cached prompt tokens when available.

Here is illustrative timing output:

prompt eval count:    2400 token(s)
prompt eval duration: 6s
prompt eval rate:     400.00 tokens/s
eval count:          180 token(s)
eval duration:       6s
eval rate:           30.00 tokens/s

With no cached input, the arithmetic is 2,400 ÷ 6 = 400 prompt tokens per second and 180 ÷ 6 = 30 generated tokens per second. The two model stages total twelve seconds before other costs. The 400-token rate describes reading the prompt; use the 30-token generation rate to estimate how quickly the answer grows.

If 2,000 of those prompt tokens were cached, only 400 would be newly evaluated. Use the uncached count when interpreting prompt-processing speed. Keep a repeated-prefix warm test separate from a fresh-document test, because they exercise different amounts of work.

For a cold comparison, unload the model with ollama stop YOUR_LOCAL_MODEL, then run the same request. Repeat while it remains loaded for a warm comparison. “Warm” should say whether you mean loaded weights, reused prompt state or both.

Use structured timing fields for a repeatable record

The Ollama generation API returns load_duration, prompt_eval_count, prompt_eval_duration, eval_count and eval_duration. Durations are in nanoseconds. Save an unstreamed response for convenient inspection:

curl http://localhost:11434/api/generate -d '{
  "model": "YOUR_LOCAL_MODEL",
  "prompt": "Explain in three sentences why the Moon has phases.",
  "stream": false,
  "options": {"num_ctx": 4096, "num_predict": 256}
}' > timing.json

Compute generation rate as eval_count × 1,000,000,000 ÷ eval_duration. For example, 180 tokens and 6,000,000,000 nanoseconds give 30 tokens per second. When the response supplies prompt_eval_cached_count, subtract it from prompt_eval_count before dividing by the prompt duration. Keep older responses without that field labeled accordingly.

Use this nonstreaming request for server timings and a streaming client or terminal run to observe first visible output. Record the model, runner version, context, output limit and whether thinking output is enabled or hidden when the model supports it.

In llama.cpp, enable internal performance timings and inspect the end-of-run report for your prompt file:

./build/bin/llama-cli -m model.gguf -c 4096 -n 256 --perf --log-verbosity 3 --single-turn -f prompt.txt

The timing labels prompt eval time and eval time identify the same broad stages. Compare like stages across runners, using the same artifact and request shape. These terminal examples apply on macOS and Linux with the appropriate runner already installed.

Optimize the stage that consumes the budget

Suppose a fresh document has 8,000 tokens and your measured uncached prompt rate is 400 tokens per second. Prompt work alone takes 8,000 ÷ 400 = 20 seconds. Reducing relevant input to 2,000 tokens would take 2,000 ÷ 400 = five seconds, saving fifteen before generation.

Now suppose generation is the issue: a 600-token answer at 30 tokens per second takes twenty seconds. An adequate 150-token answer takes five. Ask for a concise structure and enforce a suitable output ceiling, then verify that the necessary facts survive.

For parallel agents, measure the group as well as the individual. On one local GPU, agents share its throughput, and requests beyond its active capacity wait in line. Record first output, completion time and correctness for every worker, including the last one to finish.

Try it on your workload

Use one empty-history question and one version containing a representative document. Start a fresh conversation for each. Time the first visible token, last token and output count. Label cold weights, loaded weights and repeated-prefix cases separately.

Run each case three times with fixed settings. Then shorten only the supplied context and repeat. Restore the original context, shorten only the answer budget and repeat again. Your timing sheet will show which change addresses the actual delay.

Finally repeat at your expected agent concurrency. Keep the same quality rule and desktop workload. Choose the setting that makes the slowest acceptable response usable across the group.

How to decide

  • Shorten retrieved context when prompt evaluation dominates.
  • Reduce the answer budget or compare a smaller useful model when generation dominates.
  • Address loading or queues when internal generation is fast but the user still waits.

Run twenty document agents together for about two cents

Twenty document agents working at once on google/gemma-3-27b-it cost about two cents in tokens on TrustedRouter for this workload. On 2026-11-22, the live catalog listed $0.0844 per million input tokens and approximately $0.169 per million output tokens. With 10,000 input and 1,000 output tokens per agent, totals are 20 × 10,000 = 200,000 input and 20 × 1,000 = 20,000 output tokens. Cost = 0.2 × $0.0844 + 0.02 × $0.169 = $0.02026, about two cents.

On one local GPU, those agents share its throughput, and requests beyond its parallel capacity wait in line; through a per-token API, independent requests can run at the same time for the same token bill as running them one after another. Record first output, completion and correctness for each agent using the same document tasks as your local trial.

Prices change; check current rates, provider routing and agent setup, then review private API options for approved off-device work. Local remains preferable when it meets your waiting target or the work must stay offline.
