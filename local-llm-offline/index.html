How do you verify that a local LLM works offline?

Offline operation depends on the whole application. A locally stored checkpoint can still be paired with a remote embedding service, tool, login requirement or telemetry integration.

2026-11-22

Verify offline operation by disconnecting external networking, restarting the complete app and processing a new document from scratch. A successful answer from an already open chat proves less than a cold-start test covering model loading, extraction, embeddings, retrieval and saved history.

Prepare the whole application before disconnecting

Make an inventory of every component the user action touches. Download the generation model, tokenizer, embedding model, document parser dependencies and any optional speech models while connected. Keep the exact application and runtime versions with your deployment notes. Reproduce the final installation layout rather than assuming a developer cache will also exist on the destination machine.

Use a small acceptance fixture with an unmistakable fictional fact, such as a maintenance window beginning at 03:17 on Tuesday. Add that file only after networking is disconnected. Ask for the time with a source citation, close the application, reopen it and ask again. This tests ingestion and persistence in addition to cached chat behavior.

LM Studio documents local chat, local document processing and its local server as usable offline after the necessary downloads. Its model discovery, model downloads, runtime downloads and update checks use networking. Install the runtime you need before traveling; confirm the engine loads the downloaded model.

Set offline controls at the process that uses them

These controls were checked against current documentation on 2026-11-22. Apply each control to its documented component and use network rules to enforce a computer-wide boundary.

Control What it disables What to prepare
HF_HUB_OFFLINE=1 Hugging Face Hub HTTP calls in the Hub library; missing cached files cause errors All required cached artifacts
HF_HUB_DISABLE_TELEMETRY=1 Telemetry using Hugging Face Hub's telemetry mechanism Separate settings for unrelated integrations
HF_HUB_DISABLE_UPDATE_CHECK=1 Documented Hugging Face CLI update checks Installed CLI and extensions
OLLAMA_NO_CLOUD=1 Ollama cloud features, including cloud models and web search A local model and local application configuration
OFFLINE_MODE=true Open WebUI's selected downloads and update checks Local inference, embeddings and extraction

For a Python program you launch from a macOS or Linux terminal, put the variables in its environment before starting it:

HF_HUB_OFFLINE=1 HF_HUB_DISABLE_TELEMETRY=1 \
HF_HUB_DISABLE_UPDATE_CHECK=1 python3 your_local_app.py

Replace the script name with your own entry point. For a manually started Ollama server, stop any existing server first, then run:

OLLAMA_NO_CLOUD=1 ollama serve

For the macOS Ollama app, use launchctl setenv OLLAMA_NO_CLOUD 1 and restart the app. On Linux with systemd, add Environment="OLLAMA_NO_CLOUD=1" under [Service] in systemctl edit ollama.service, reload systemd and restart Ollama. Confirm the log reports Ollama cloud disabled: true.

Open WebUI's current offline setting also sets Hugging Face offline mode, disables its version check and disables automatic embedding, reranking and Whisper model updates. Configure the embedding and extraction providers themselves as local. The interface can otherwise be local while a document-processing service remains remote.

Distinguish a working offline app from blocked outbound traffic

There are two tests. The availability test asks whether the required functions work without external services. The containment test asks whether the deployment can contact external destinations. Test both separately: an optional updater could attempt a request while local generation succeeds.

For a single laptop, disconnect Wi-Fi, Ethernet, tethering and other external paths while leaving loopback available to local services. For an isolated multi-machine installation, keep only its permitted internal network. If you need evidence of blocked attempts while network interfaces stay active, use administrator-managed outbound rules and their logs. Use listening addresses to restrict incoming access and outbound rules to restrict outgoing requests.

Remove remote tool connectors and hosted endpoints from the offline profile. Make missing local models fail clearly instead of falling back to a cloud route. Test authentication too: a local inference service is of little use if its interface cannot open without an unavailable external login.

Keep offline and connected profiles distinct. A visible profile name helps operators recognize which boundary applies. Do not automatically re-enable a remote tool after a timeout; that changes where the document goes at exactly the moment the user expects local behavior.

Try it on your workload

  1. While connected, install the selected versions and download every artifact. Record paths and confirm the exact workflow works once.
  2. Close all components, apply their offline settings and remove external network access. Restart the browser or desktop app and all local services.
  3. Import a fresh fictional document, retrieve its distinctive fact, generate an answer and verify its source. Use a new conversation.
  4. Save, close and reopen the conversation. Restart the machine if the deployment will need to recover from power loss.
  5. Try an unavailable model and a disabled web tool. Verify a clear failure rather than an attempted hosted fallback.
  6. Record blocked connection attempts when network controls provide logs, and repeat after each runtime or plugin upgrade.

Keep a result sheet with one row per operation: startup, ingestion, retrieval, generation, persistence and recovery. Separate functional failures from optional network attempts. This makes a missing embedding cache easy to distinguish from a broken model runner.

How to decide

  • Call the workflow offline-ready only when every required operation passes after a cold start.
  • Use network controls for an enforced boundary; configure the application to avoid unnecessary requests and report missing local dependencies clearly.
  • Keep hosted inference disabled for data whose execution policy requires staying offline.

Run ten connected evaluation agents for about a fifth of a cent

Ten connected evaluation agents working in parallel on 100 fictional examples on openai/gpt-oss-20b cost about 0.2 cents in tokens on TrustedRouter. On 2026-11-22, the live catalog listed approximately $0.01 per million input and $0.0475 per million output tokens. Each agent processes ten examples with 1,000 input and 200 output tokens each: 10 × 10 × 1,000 = 100,000 input and 10 × 10 × 200 = 20,000 output. Cost = 0.1 × $0.01 + 0.02 × $0.0475 = $0.00195, about 0.2 cents.

On one local GPU, those agents share throughput, and requests beyond its parallel capacity wait in line; through a per-token API, independent requests can run at the same time for the same token bill as sequential execution. Keep this connected profile separate and enable it deliberately for public or approved material.

Prices change; check current prices and agent setup. The confidential API guide describes requiring encrypted provider inference and zero data retention, subject to model and provider availability. Local is the better choice when the workflow must operate without a network or keep data on the device.
