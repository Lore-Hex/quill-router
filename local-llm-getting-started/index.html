Should you run your first LLM locally?

Start with a task you can recognize as correct. A useful first experiment is to turn a fictional meeting transcript into decisions, owners and deadlines.

2026-11-22

Run your first LLM locally if you need offline use and can judge five representative answers yourself. Give the experiment one hour on hardware you already own; buy nothing until it passes your accuracy and waiting-time limits.

Spend the first hour on one small task

Start with fictional meeting notes and ask for decisions, owners and deadlines. Write the expected answer before opening a chat. A useful first result preserves an unknown deadline instead of inventing a plausible date. Set a personal time limit, such as 30 seconds per short transcript; use that acceptance target to decide whether the result is useful.

Spend the first 15 minutes installing and downloading, the next 15 getting an answer, and the remaining 30 checking five examples. Downloads or driver setup may exceed that budget. Record the obstacle rather than treating a long installation as evidence about model quality.

On macOS, open ollama.dmg, drag Ollama into Applications and launch it. Accept the CLI setup prompt if shown; it creates a link in /usr/local/bin. Then open Terminal and run the shared model commands below. This installation path is documented by Ollama as of 2026-11-22.

On Linux, download the official installer, inspect it, then run it:

curl -fsSL https://ollama.com/install.sh -o ollama-install.sh
less ollama-install.sh
sh ollama-install.sh

On either macOS or Linux, continue with:

ollama -v
ollama pull llama3.2:3b
ollama ls
ollama run llama3.2:3b

If the server is not running, start ollama serve in a separate terminal, then retry. The explicit llama3.2:3b tag identifies a small starting model: Ollama lists its download at 2.0 GB. Budget additional working memory for the cache and runtime. Keep the version printed by ollama -v and the chosen model tag beside your results.

At the chat prompt, paste this fictional example. The triple quotes are Ollama's documented multiline-input syntax:

"""Extract only agreed decisions, owners and deadlines.
Use unknown when an owner or deadline was not agreed.
Transcript: Maya proposed shipping Friday. Luis said testing was incomplete.
They agreed to postpone the release. Maya will send a revised plan.
Nobody agreed to a date for the plan or the release.
Return one line per agreed decision or task: decision or task, owner, deadline."""

The reference answer postpones the release, assigns Maya the revised plan, and leaves both dates unknown. While the model is loaded, run ollama ps in another terminal. Its processor column distinguishes GPU, CPU and mixed placement. Record the loaded model ID and save the answer unchanged before editing your prompt.

Match hardware to an actual model artifact

Start with the same small model on your existing hardware, then check its placement with ollama ps. CPU inference uses system memory; GPU inference needs available accelerator memory. Ollama also supports Apple GPU acceleration through Metal. Check its hardware-support page for your exact device and driver before making a purchase.

Hardware class What to try Memory and setup
CPU-only computer with spare system memory llama3.2:3b Ollama supports CPU placement; this artifact is a 2.0 GB download. Measure its loaded footprint and your wait.
Supported desktop GPU or Apple GPU The same llama3.2:3b baseline Ollama documents GPU support. Confirm actual placement with ollama ps instead of assuming acceleration.
Machine with a 16 GB model-memory budget gpt-oss:20b in Ollama OpenAI's model card says its MXFP4 version runs within 16 GB of memory. Check that your laptop has enough free memory after accounting for its other applications.
Single 80 GB GPU gpt-oss-120b with a compatible runtime The same model card documents this fit with MXFP4 weights. Consider this larger-capacity option after completing the first-hour experiment.

Longer contexts and simultaneous requests need additional memory; Ollama's FAQ explains that parallel requests increase context allocation. Begin with short transcripts and one request. For example, four parallel requests with a 2,048-token context allocate 2,048 × 4 = 8,192 context tokens under that rule. Leave room for applications and check the longest input you actually expect. Agents on one local GPU share its throughput, and requests beyond its serving capacity wait in line.

Try it on your workload

Create five short fictional transcripts: an agreed task and date, an absent deadline, a rejected proposal, a reassigned owner, and two tasks with different dates. Write a reference list of commitments for each. Use the prompt above, substituting each transcript, and start a fresh chat for each case.

Record the prompt, runner version, model ID, raw answer, elapsed seconds, missed commitments and invented commitments. Repeat all five with the same settings. Ten answers give you ten opportunities to check whether a missing date stays missing. Treat an invented commitment as an error even when the rest reads well.

Then repeat with networking disconnected if offline use is your requirement. For an approved hosted comparison, send those same fictional fixtures and score them with the same reference answers. Compare review time as well as generation time.

How to decide

  • Keep local inference when offline operation matters, the repeated answers meet your accuracy rule, and your machine finishes within your chosen time limit.
  • If accuracy fails, compare another model on the same five inputs before buying hardware. More spending needs evidence from accepted answers.
  • If you only occasionally need a larger model or several agents at once, price those bursts through an API and compare the outputs.

Run ten summary agents at once for about 2 cents

Ten summary agents working at once on openai/gpt-oss-20b cost about 2 cents in tokens on TrustedRouter for the workload below. After your five local fixtures pass, use the same acceptance rules to compare a larger set of approved meeting notes.

On 2026-11-22, the live catalog listed rounded rates of $0.01 per million input tokens and $0.0475 per million output tokens. In this illustrative workload, each agent uses 100,000 input and 20,000 output tokens across its requests. Input = 10 × 100,000 = 1,000,000; output = 10 × 20,000 = 200,000. Cost = 1 × $0.01 + 0.2 × $0.0475 = $0.0195, about 2 cents.

On one local GPU, those agents share throughput, and requests beyond its parallel capacity wait in line; through a per-token API, they can work at the same time for the same token bill as running one after another. Prices change; check current prices and agent setup. For approved off-device work, encrypted inference and zero data retention depend on model and provider; check the eligible route's price. Local remains better when your data must stay offline.
