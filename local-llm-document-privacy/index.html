Where can private documents go in a local LLM app?

Trace a document through ingestion, embeddings, retrieval, generation and logging. Each stage can have a different storage location or service owner.

2026-11-22

A private document can become an uploaded file, extracted text, search-index content, prompt context, chat history and a backup. Trace all six copies before calling an application private; selecting a local generation model settles only one stage of that path.

Draw the document's route before uploading it

Start with the original file on your laptop. Identify the process that receives the upload, the parser that extracts its text, the embedding service, the vector store and the generation endpoint. Then add the interface's saved conversations, operational logs and backup destination. Write the owner and configured address beside every service.

Stage Data to account for Concrete check
Ingestion Original file and extracted text Locate the upload directory and parser endpoint
Embedding Text sent to the embedding model and returned vectors Check the embedding provider independently of chat
Retrieval Stored chunks, source metadata and search queries Inspect the index and its access rules
Generation Question plus selected source passages Confirm the actual model endpoint
History and operations Answers, citations, logs, exports and backups Record locations, readers and retention

For each arrow, ask whether the receiver runs on the device, on an internal server or outside your organization. Check the backend's address even when the browser runs locally. A remote embedding call can transmit document text even when the final answer comes from a GPU under your desk.

Use separate approved configurations for separate data classes. If a document must stay on one device, an internal network server is still outside that device. Make the requirement explicit enough that someone configuring the app can tell whether a destination qualifies.

Know what the common stacks actually store

Ollama's FAQ says locally run prompts and data are not sent to Ollama. Its documented model directories are ~/.ollama/models on macOS and /usr/share/ollama/.ollama/models for the standard Linux installation, overridable with OLLAMA_MODELS. Those are model-storage paths. Inspect the client application's document and history storage separately.

LM Studio's current chat documentation places conversations at ~/.lmstudio/conversations/ on macOS and Linux. They are JSON files; use the chat's Reveal in Finder or corresponding file-reveal action to locate the actual file. Do not write a deletion tool against an assumed internal JSON structure.

LM Studio's privacy policy, updated October 19, 2026, says local models keep messages, histories and documents on the device and that the application does not include telemetry or user-specific tracking. It separately describes network use for search, downloads and updates, and optional cloud processing. Review optional cloud features separately from the local workflow.

Open WebUI default Docker data location Contents to inspect
/app/backend/data/uploads/ Uploaded files
/app/backend/data/vector_db/ Local ChromaDB vector store
/app/backend/data/webui.db SQLite application data
/app/backend/data/cache/ Cached data

Open WebUI's backup guide documents these components. Map the container data directory to its persistent host volume and record the backup destination separately. If your deployment uses an external database, vector service or object store, inventory that configured service instead of relying on this default layout.

Review access, logs and deletion together

Open WebUI documents chat content as plain JSON in its database, uploads as unencrypted application files and document chunks as text in the vector store unless additional protection is configured. Use storage-layer encryption and protect backups separately. The running application still needs access to serve authorized users.

Its ENABLE_ADMIN_CHAT_ACCESS=false and ENABLE_ADMIN_EXPORT=false controls hide interface capabilities; they do not exclude infrastructure operators from the data. Temporary Chat reduces saved history but still sends the active prompt to the selected model and permits enabled tools to run. Treat operators and tools as explicit parts of the boundary.

ENABLE_ADMIN_CHAT_ACCESS=false
ENABLE_ADMIN_EXPORT=false
AUDIT_LOG_LEVEL=METADATA

Review these Open WebUI deployment settings alongside storage encryption, access and backup controls. Its documentation distinguishes metadata audit logging from request and response body logging. Avoid putting document bodies into diagnostic output merely to troubleshoot a timeout.

Write a deletion checklist before the first real upload: original upload, extracted representation, indexed chunks, conversations that quote the source, exports and backup retention. Removing a document from a sidebar is one action in that checklist. Treat vectors and their metadata as derived document data rather than an anonymous substitute for the source.

Keep the backup policy practical. Record who can restore it, how long snapshots remain and how a restore avoids reviving records that were intentionally removed. A system can stop retrieving a document today while an older copy remains in its retention window.

Try it on your workload

Create a fictional document containing the unique marker CEDAR-PRIVACY-7319 and a made-up delivery date. Upload it through the normal interface, retrieve the date, and make the assistant cite the passage. Keep the marker out of your question so finding it demonstrates access to the document.

Inspect the configured upload store, index, chat export and permitted logs using their normal administrative tools. Record every location that contains the marker or a reference to its source. Inspect a test backup too, using a disposable restore environment rather than modifying the live database.

Delete the document through the supported interface, then begin a fresh conversation and repeat retrieval. Check any old conversation that quoted the text separately. Record residual copies and their retention deadlines. Finally, repeat the workflow with external networking blocked to detect any extraction or embedding dependency you overlooked.

How to decide

  • Approve each processing and storage stage for the document's data class.
  • Choose a device-only stack when no off-device processing is allowed.
  • Accept a shared local service only when its operators, backups and access model also meet the requirement.

Review ten approved documents in parallel for about two cents

Ten document agents working at once on meta-llama/llama-3.3-70b-instruct cost about two cents in tokens on TrustedRouter for this fictional-document trial. On 2026-11-22, ordinary catalog rates were approximately $0.142 per million input and $0.422 per million output tokens. Ten agents with 10,000 input and 1,000 output tokens each use 100,000 input and 10,000 output tokens. Cost = 0.1 × $0.142 + 0.01 × $0.422 = $0.01842, about two cents.

On one local GPU, those agents share throughput, and requests beyond its parallel capacity wait in line; through a per-token API, independent document requests can run at the same time for the same token bill as serial execution. Keep the inventory of files, indexes and histories your application retains.

For approved documents, confidential routing can require encrypted provider inference and zero data retention; availability depends on model and provider. Check the selected route's price separately from this ordinary catalog example. Prices change; review current prices, data visibility and agent setup. Choose local processing when documents must remain on the device.
