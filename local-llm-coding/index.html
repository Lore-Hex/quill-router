Is a small local coding model good enough for your repository?

Use a real maintenance task with a testable outcome. A plausible-looking patch is a weak measure if it calls an API your project never used.

2026-11-22

A small local coding model is good enough when it produces an accepted patch on your repository with less total waiting and review than your alternative. Start with two reproducible maintenance bugs, and judge the complete edit-and-test loop rather than a single generated function.

Budget context for the complete coding session

An agent's working context includes instructions, tool definitions, source files, search results, previous edits and test output. Reserve space for the next response as well. As of November 2026, Ollama's context documentation recommends at least 64,000 tokens for agents and coding tools. Start there if your memory budget permits, then check placement and response time.

Here is an illustrative 64,000-token allocation: 4,000 for instructions and tools + 30,000 for source + 12,000 for history and test output + 8,000 for the next answer = 54,000, leaving 10,000 tokens of margin. Replace them with counts from your agent's actual requests before sizing hardware.

In the Ollama desktop app, change the context slider in settings. For a manually launched server on macOS or Linux, stop the existing server first and use:

OLLAMA_CONTEXT_LENGTH=64000 ollama serve

In another terminal, use ollama ps to inspect the loaded model's context and processor placement. The environment variable applies to the server you launch; use the settings slider for an already running desktop app. Larger context requires more memory, so keep irrelevant logs and repeated file dumps out of the conversation.

Parallelize independent work in separate worktrees

Coding is an especially useful place to add parallel agents because maintenance work often divides into independently testable changes. One agent can fix date formatting while another repairs a command-line error message and a third investigates a failing fixture. Each gets a bounded task, a test command and its own working directory. Review and integration remain explicit steps.

Git worktrees provide multiple working trees attached to one repository. Starting from your chosen baseline, these commands create two new branches and directories on macOS or Linux:

git worktree add -b agent-date ../agent-date HEAD
git worktree add -b agent-cli ../agent-cli HEAD

Run each agent inside its assigned directory. Give it only the files and dependencies relevant to its task, and keep separate output paths for generated artifacts. Worktrees separate file edits; coordinate design decisions and isolate shared external databases separately.

On one local GPU, concurrent agents share available throughput and queue when capacity is occupied. Ollama's FAQ also explains that parallel requests increase context allocation. Four requests configured for 64,000 tokens represent 4 × 64,000 = 256,000 context tokens under that allocation rule. Budget memory and throughput together when adding agents.

For an illustrative local scheduling example, suppose four independent tasks each take 15 minutes when run alone. Serial time is 4 × 15 = 60 minutes. Four separately provisioned local machines could each run one 15-minute task, followed by review and integration. Compare that hardware requirement with your actual task volume.

Try it on your workload

Freeze a revision with a known formatting bug and an existing test that exposes it. Supply every candidate with the same issue description, relevant files and permitted commands. Require a patch, the test result and a short explanation of why the change fixes the case. Do not reveal a reference patch in the prompt.

Record time to the first passing patch, total time including review, failed test runs, unrelated changed lines and invented APIs. Check a neighboring case the agent did not see. If the repository uses two languages, repeat with a second bug in the other language. A model that succeeds on Python should still earn its place on your TypeScript task.

Next run the two tasks simultaneously in separate worktrees. Compare wall-clock time and accepted patches per hour against the serial run. Keep the same model, prompt and test environment so the experiment isolates scheduling rather than a simultaneous model upgrade.

How to decide

Keep local coding for focused changes that pass tests and review within your working time budget. Improve file selection when context is crowded. Compare a stronger model when the agent sees the right evidence but repeatedly produces incorrect fixes. Rent additional capacity when independent tasks are ready and inference queues, rather than human review, delay completion.
