How do you choose the right GGUF file?

GGUF packages model tensors and metadata for compatible runtimes such as llama.cpp. A filename can combine a model revision, parameter size and quantization. Check each independently.

2026-11-22

Choose a GGUF by checking its upstream checkpoint, quantization, runtime support and exact file identity before downloading. Keep one record containing the publisher, revision, byte size and checksum; use that record to reproduce an evaluation.

Know what the file contains

GGUF stores model tensors and typed metadata for GGML-based inference tools. The specification includes architecture information and tokenizer metadata, including an optional chat template. Hugging Face's file viewer exposes GGUF metadata and tensor information, so you can inspect more than a filename before committing to a large download.

Think of the format as packaging. The model checkpoint determines the learned weights, quantization determines their representation, and the runtime must understand the architecture and tensor types. After identifying the .gguf packaging, check all three properties before selecting the file.

The GGUF naming convention separates a base name, size label, fine-tuning description, version, encoding and optional shard information. Publishers do not always follow the convention perfectly. Read the model card and file metadata together, and resolve any disagreement before using the file in a comparison.

Part to check Example meaning What to save
Upstream checkpoint The original model and revision used for conversion Repository and immutable revision
Variant Base model, instruction tuning or another adaptation Publisher's model-card description
Encoding A quantization recipe such as Q4_K_M Exact filename and actual byte size
Shard suffix 00001-of-00002 identifies one part of two Every required part and its checksum
Runtime The build that successfully loaded the architecture Version, settings and a smoke-test answer

Check provenance and size before the download

Follow the conversion publisher's link to the upstream model. Record both identities: the organization that trained or released the checkpoint and the organization that converted it. Read the applicable license files and intended-use notes instead of assuming that a downloadable artifact has the terms you need.

Choose two plausible quantizations at most for the first experiment. For illustration, downloading a 5 GB file and a 6 GB file requires 5 + 6 = 11 GB of storage before any other artifacts. That storage budget is distinct from the memory needed to load either model and its conversation cache.

Use the quantization comparison to decide which pair to try. Preserve the upstream checkpoint while changing precision. Hold the fine-tune fixed to identify what quantization changes.

For split files, collect all the parts belonging to the same revision. Ollama's current import documentation requires the original split filenames and a wildcard matching every shard. You need the complete shard set to use the model.

Verify the bytes and inspect metadata

If the publisher supplies a SHA-256 checksum, compare it with the downloaded file. This Python snippet works on macOS and Linux with Python 3 installed and reads the file in chunks rather than all at once:

python3 - <<'PY'
import hashlib
from pathlib import Path
path = Path("model.gguf")
digest = hashlib.sha256()
with path.open("rb") as source:
    for chunk in iter(lambda: source.read(1024 * 1024), b""):
        digest.update(chunk)
print(path.stat().st_size, digest.hexdigest(), path.name)
PY

Replace the filename with your actual artifact. A matching checksum confirms that your bytes match the published digest. Evaluate model quality and publisher trust separately. If no digest is supplied, save your own as an identifier for the file you evaluated.

The llama.cpp repository provides a GGUF metadata-dump tool. From an existing checkout, install its Python package in your chosen environment and inspect the artifact:

python3 -m pip install ./gguf-py
python3 gguf-py/gguf/scripts/gguf_dump.py model.gguf

Look for general.architecture, the tokenizer fields and tokenizer.chat_template when present. Save the dump with the evaluation. Do not “fix” unexpected metadata by editing it until the file's origin and intended runtime behavior are understood. A metadata edit creates a different artifact that deserves a new checksum.

Run a smoke test before a benchmark

Use one prompt supplied by the model card, then one short task whose answer you already know. For example, ask it to extract the quantity from “We ordered seven boxes; two are replacements” and verify that it preserves the distinction. Check the formatting and stopping behavior as well as the content.

To import a compatible single-file GGUF into Ollama, create a file named Modelfile with the following content, substituting your absolute path:

FROM /absolute/path/model.gguf

From that directory, run:

ollama create local-artifact
ollama run local-artifact

Ollama imports GGUF weights in their existing quantization. Prepare the quantization beforehand. If the smoke test fails to load, capture the exact error and build version before trying unrelated prompt changes.

Try it on your workload

Build an artifact record containing the publisher, upstream checkpoint, revision, license link, filename, byte size, checksum and successful runner build. Include every shard when applicable. Have a colleague use that record to obtain and identify the same file.

Run the model-card prompt and five representative tasks. Save the raw answers and settings. Repeat after restarting the runner. If you compare another file, change one property at a time and label the result with its own artifact record. Keep the original files until you have finished investigating any disagreement.

How to decide

  • Keep the artifact when its provenance is clear, your runtime loads it correctly and it passes the task checks.
  • Resolve a checksum mismatch, missing shard or unsupported architecture before judging answer quality.
  • Preserve exact artifact identifiers beside results so a later download does not silently replace your baseline.
