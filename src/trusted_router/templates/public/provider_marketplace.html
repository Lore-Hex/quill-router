New provider requirement

Start with one verifiable confidential model.

Choose the exact model, endpoint and release you want us to verify. Other models may be listed without this designation. A chip name, ordinary HTTPS, or a zero-retention promise alone is not proof of confidential inference.

Need help setting up confidential compute?

Talk to provider operations before you apply. Tell us which model you serve, your host CPU and GPUs, and where inference runs. We can work with you to choose a supported configuration, set up attestation, and test your first endpoint together. No keys or customer data, please.

Examples of capable hardware include H200 on supported Intel TDX hosts (protected PCIe for multi-GPU Hopper), Blackwell B200 and HGX B300. See NVIDIA's supported configurations. Vera Rubin NVL72 supports rack-scale confidential computing with Vera CPUs and Rubin GPUs. In each case we verify the deployed workload and its actual devices and connections, not the product family.

Test the endpoint you will submit

  1. Publish the reference. Give us the model ID, immutable source and release, signed build measurements, and how model weights are protected when loaded. Do not use values learned from the running endpoint as your expected values.
  2. Verify before sending. Check fresh hardware-signed evidence against vendor roots and the release. Cover the CPU, every serving GPU, relevant switches and downstream hops; check production mode and bind the inference connection or encryption key to that verified workload.
  3. Prove both outcomes. Send a synthetic request through the verified client. In staging, show that stale evidence, a wrong key or release, and corrupted weights prevent inference. Never fall back to ordinary HTTPS or an unverified replica.
  4. Share a reproducible result. Provide verifier commands, versions, a dated redacted result, and evidence for all eligible replicas. We repeat the checks ourselves before listing the route as confidential.

Run the confidential endpoint self-check from our open-source checker. Tinfoil's verified client is one example, not a required vendor. The ordinary API conformance suite does not attest hardware.

Prompt for Claude: check my confidential endpoint

Audit the exact production model route I name against the TrustedRouter confidential endpoint guide. Start with my independently signed release reference. Trace where the prompt is decrypted, how the client verifies the workload key, which CPUs, GPUs, switches and replicas can serve it, how weights are verified on read, and whether logs or fallback routes expose plaintext. Use the maintained verifier for this platform. Ask before sending synthetic traffic or disclosing device evidence. Test rejected cases in an isolated fixture, never against customer workloads. For each requirement report PASS, FAIL or NOT TESTED with a command and redacted evidence. Never infer a pass from a SKU, HTTP 200, or my assertions. Do not request or print secrets, grant a badge, or change production.

Privacy evidence

State what happens to request data.

  • Content and metadata. Give retention and deletion rules for prompts, outputs, uploaded files, prompt caches, logs, and backups separately. List retained operational metadata and its retention period.
  • Training and exceptions. Cover your own service and all subprocessors, including abuse monitoring, human access, and opt-in or opt-out settings.
  • Applicable ZDR terms. Link the inference-specific policy or provide the agreement for our account through an agreed secure channel. Identify covered models, tiers, regions, and required settings. No training is not the same as zero retention.
  • Confidential inference. Supply verifier instructions, attestation endpoints, source and immutable releases, and expected measurements. Explain encryption-key binding, GPU and downstream verification, and whether operators can access workload memory or keys. SOC 2 or encryption in transit alone does not establish E2EE.
Inference locations

Where can each route actually run?

  • All possible locations. List countries or broad cloud regions for each model and tier, including downstream hosts and failover destinations. A headquarters address is not an inference-location guarantee.
  • Dynamic routing. Say whether placement can change per request or over time, and how customers are notified. If global or unknown, say so explicitly.
  • Pinning and returned evidence. Document the exact region parameter and allowed values, whether failover stays within it, and the response field or header reporting the actual serving region. Say when either feature is unsupported.
  • Data residency. Separately identify storage, logging, prompt-cache, and backup locations and link the applicable residency commitment.
Energy and sustainability

Is your inference powered by 100% renewable energy?

Answer Yes, Partly, No, or Unknown. If partly, give the renewable electricity percentage. Cover the infrastructure that will serve TrustedRouter requests, not just your offices or a company-wide target.

Include inference GPUs and supporting datacenter electricity, every applicable facility and region, downstream providers, and failover capacity. Name any exclusions or routes whose energy mix is unknown.

Show the basis of the claim.

  • Scope and date. Specify covered models, regions and operators, the reporting period, measurement method, and next review date.
  • Procurement and matching. Distinguish on-site renewable generation, power purchase agreements (PPAs), renewable energy certificates (RECs) or Guarantees of Origin, and hourly versus annual matching.
  • Evidence. Link a facility or electricity-supplier disclosure, sustainability report, or independent assurance covering the declared scope. Arrange secure review of non-public evidence.
  • No substitutions. Carbon offsets, carbon-neutral claims, and future targets do not establish 100% renewable electricity. Report them separately. A provider declaration is not independently verified certification.

Provider Reliability Contract v2

Copy this output exactly.

Do not design a custom catalog or pricing format. Return one unpaginated JSON document from GET /v1/models. Put capabilities, prices, lifecycle, model deadlines, regions, and overload semantics in the machine-readable response.

  • Use exact decimal strings. Every price is USD per one million tokens. Use "0.50", never a JSON float.
  • Use null when a cache rate does not apply. Do not omit required fields.
  • Use lowercase stable IDs. The format is provider/model-name. Never recycle an ID for a different model.
  • Use UTC timestamps. Lifecycle timestamps use RFC 3339, for example 2026-08-05T00:00:00Z.
  • Use one row per billable tier. If rates or capabilities differ, publish a distinct stable model ID for that tier.
  • Document task-specific endpoints. Add the optional documentation object with a plain-text description, input and output guidance, and one representative example. TrustedRouter renders it on the model page.
  • Separate overload from account quota. Return 503 for temporary serving capacity, 429 for request rate limits, and a stable account-quota error code when TrustedRouter must provision more quota.
  • Always send Retry-After. Fast, explicit backpressure lets TrustedRouter roll over immediately instead of letting requests hang.
  • Publish model deadlines. First-token, completion, and stream-idle budgets are evaluated per model rather than with one global timeout.

Open-source preflight

Run the conformance suite before you apply.

Run the TrustedRouter provider checker against the same production API base you plan to submit. It tests catalog discovery, advertised model callability, chat completions, streaming, usage, tool calls, errors, and first-token behavior against the contract expected by TrustedRouter's attested gateway translator.

The suite is open source under Apache-2.0 and works with any conformant serving stack.

  • Tiers 1–4 are the conformance gate. A hard failure exits with status 1, so the checker works in CI.
  • Credentials stay local. Use TR_PROVIDER_API_KEY to keep the key out of shell history. Reports recursively redact it.
  • Checks make real requests. The model sweep and chat probes use real, billable completion calls. The default sweep is bounded to 25 advertised models.
  • Keep the report. Attach the redacted JSON artifact to your application so failures can be reproduced quickly.

Acceptance check

These two calls must work.

The catalog request must match the published schema. The chat request must return a normal OpenAI chat completion with nonzero token usage.

  • HTTP 200 with Content-Type: application/json
  • choices[0].message.content contains PONG
  • usage.prompt_tokens, usage.completion_tokens, and usage.total_tokens are integers
  • The response model identifies the model that actually ran

If your API cannot implement this contract, email the same address with the incompatibility. Do not invent a second format.

Contract v1 covers chat-capable models. Include embeddings, image generation, audio, or other APIs in the email and we will map them separately.
