Know the route behind the model name

An API's model label tells you what the service says it selected. Stronger verification connects that selection to a known provider, a reviewed configuration and, where supported, an attested inference workload. TrustedRouter brings these checks into one workflow so you can make a better-informed choice before sending production traffic.

Start with a non-sensitive evaluation prompt. Record the exact endpoint, model ID, provider and request settings. Then use the steps below to distinguish a routing record from evidence about the code and weights that actually ran. Asking an assistant “what model are you?” is not an authentication method: generated text can repeat a supplied name.

1. Pin the model and provider for your evaluation

Use an explicit catalog model ID rather than a convenience selector such as trustedrouter/auto. Choose a provider from the model's endpoint list. In TrustedRouter, provider.only restricts the provider set and allow_fallbacks: false prevents a request from continuing to another candidate. That makes an evaluation easier to reproduce; it does not prevent the provider itself from updating a moving model alias.

{
  "model": "AUTHOR/MODEL",
  "messages": [{"role": "user", "content": "Reply with PONG."}],
  "provider": {
    "only": ["PROVIDER_SLUG"],
    "allow_fallbacks": false
  }
}

Replace both placeholders with a currently available model and provider. See routing and pinning for accepted controls and errors. Pinning intentionally trades some availability for a stable route.

2. Check the published serving configuration

Open the model's provider list and inspect the precision evidence. Reviewed endpoints can include weight formats, model revision, serving-code links and a review date. Weight precision and KV-cache precision are separate. Unknown values remain unknown rather than being inferred from a model name.

This information helps you compare like with like. It is a reviewed configuration snapshot, not a live measurement of every request: the precision metadata explicitly reports runtime_verified: false. Use the precision metadata API to retain the evidence you evaluated.

3. Keep a verifiable record of the routed response

Opt-in signed inference receipts bind request and response hashes to the gateway's recorded model, provider, endpoint and upstream verification tier. Verify the signature, attestation chain and your nonce with the documented verifier. Keep the receipt with your evaluation record; an unsigned response field is a weaker form of evidence.

The receipt authenticates the gateway's record. A model name inside it is not automatically a measurement of a remote provider's weight files. Receipts are also separate from confidentiality and have their own pricing; check those terms before enabling them for all traffic.

4. Verify the inference workload when identity matters

Confidential compute adds an important tool: hardware-rooted evidence about the environment receiving your request. For stronger model identity, the measured serving application must bind and enforce the expected model artifacts, not merely run inside a TEE. Verify that evidence against a reference you approve and bind the encrypted connection to the verified workload.

TrustedRouter offers verified confidential routes and an attested gateway. Inspect the selected provider's evidence; do not extend a gateway guarantee to every upstream endpoint. The attestation guide explains what to ask for at each boundary.

5. Test quality as a separate question

Run your task set with fixed prompts, tools, context and generation settings, with enough samples to measure variation. Compare task success, latency and cost. A verified model can still give a poor answer, and different answers do not by themselves prove substitution. Model Equality Testing studies distributional differences; it is not a cryptographic identity check.

The practical win is a repeatable evaluation: a pinned route, dated configuration evidence, a verified response record and an explicit attestation scope. You can use those records to investigate a regression without guessing which layer changed.
