Turn an opaque API into an evidence-based decision

Model substitution means a service supplies a different model or deployment than the one it represents to the buyer. The useful response is to ask for better evidence. TrustedRouter helps you choose an explicit route, inspect available configuration sources and verify signed records and confidential-workload evidence.

Start by separating an undisclosed change from a documented product feature. A router that clearly selects among models is not promising a fixed checkpoint. A version alias may intentionally track newer releases. A disclosed quantized deployment can be a good price-performance choice. What matters is whether the service description, routing policy and delivered behavior agree.

What the research actually found

The September 2026 revision of Real Money, Fake Models, accepted at CCS 2026, reports behavioral inconsistencies and fingerprint evidence consistent with deceptive claims in a subset of audited shadow-API endpoints. Its sampling and statistical tests do not establish a market-wide fraud rate, and the study is not evidence that every aggregator substitutes models.

In Are You Getting What You Pay For?, researchers examine substitution detection and limitations of output-based methods, including subtle and adaptive changes. They discuss TEEs as a possible path toward stronger integrity evidence. That supports a layered evaluation rather than treating a few benchmark questions as conclusive proof.

Developer interest is visible in projects such as Modelprint, which compares observable endpoint behavior and infrastructure clues. Such tools can help formulate questions for a provider. Their results are not a hardware-signed statement about loaded weights.

Four changes to distinguish

Different model
A different family, size, checkpoint or fine-tune is selected. Ask whether that is allowed by the route's documented policy.
Different precision
The same model family runs with different weight or cache formats. Evaluate the disclosed configuration on your task; quantization is not inherently deceptive.
Different serving configuration
Prompt templates, context truncation, sampling and tool handling can change results without replacing the weights.
Different route over time
An alias, fallback policy or provider update changes which deployment handles a request. Preserve version and route records to identify the change.

A practical provider evaluation

Ask for the exact model version, available precision evidence, fallback policy and update policy. Run a non-sensitive reference workload, then repeat it with the provider pinned. Measure task quality and response distributions rather than judging a single answer. Keep latency and token-usage changes as diagnostic signals, not verdicts.

On TrustedRouter, inspect reviewed precision metadata, pin a route with provider controls, and use signed receipts when you need an authenticated gateway record. Unknown configuration remains unknown. Current precision snapshots are marked runtime_verified: false, so they should not be presented as per-request weight proofs.

Why confidential inference changes the conversation

A well-designed confidential inference deployment lets a client verify the execution environment before releasing sensitive data. For model identity, that design must also commit to and enforce the model artifacts. This is stronger evidence than a self-reported model label when the full verification chain is present.

TrustedRouter's gateway attestation and selected confidential upstream routes make that evidence easier to evaluate. Ask which workload was measured, which artifacts it binds, and how the connection is tied to it. A gateway TEE alone cannot establish every remote model's weights. Use the verification checklist to keep the claim matched to the evidence.

Document a concern without jumping to an accusation

If results change, preserve the timestamp, model identifier, provider, parameters, receipt and configuration sources. Reproduce the issue, compare a documented reference and ask the provider to explain the discrepancy. An evidence-led conversation can reveal a harmless configuration difference, an integration bug or a material mismatch. Each calls for a different fix.
