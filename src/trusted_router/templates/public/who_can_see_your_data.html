Who processes a request?

Prompt TLS terminates inside an attested enclave running published source. The TrustedRouter control plane never receives production inference prompt or output bodies, and ordinary inference keeps no prompt or output logs. Anyone can verify the running image against the published release using the evidence on the trust page.

What this does not change

TrustedRouter adds a company and a gateway to the request path. The attested gateway processes your prompt in memory. The control plane handles account and billing metadata. The upstream provider still processes the prompt and receives the content needed to run the model. Its privacy terms depend on the route you select; bound the upstream with provider.only and provider.min_privacy.

Calling a provider directly means trusting that provider's policy document. Through TrustedRouter, the gateway hop is verifiable, and you can restrict the upstream per request to zero-retention or confidential routes with provider.min_privacy, failing closed if no eligible route remains. The selected provider's retention policy still matters.

Verify the gateway hop

The hosted API runs in an attested enclave. The trust page publishes the source commit, image digest, source repositories, and verification prompt. Follow its current release evidence rather than copying a digest from this page.

  1. Fetch https://api.trustedrouter.com/attestation over normal public TLS.
  2. Verify the JWT signature and issuer https://confidentialcomputing.googleapis.com, and the audience quill-cloud.
  3. Compare the attested image digest with the accepted release measurements on the trust page and in gcp-release.json. Follow the published source commit to inspect the gateway code.
  4. Check that the TLS certificate fingerprint is bound into the attestation nonce, so the evidence belongs to the connection you use.

These checks bind the connection to the measured gateway workload and its published release. They do not make the upstream provider confidential or prove its retention policy. The ordinary OpenAI SDK example in simple start does not perform these attestation checks for you.

Optional signed inference receipts identify the serving model, provider, and upstream verification mechanism and bind the request and response bytes. A receipt proves integrity and origin, not confidentiality or upstream retention. Archive the receipt and matching attestation yourself if you need that evidence.

Bound the upstream explicitly

Provider routing and pinning documents the actual request fields. provider.only is a hard provider allowlist. Set provider.allow_fallbacks: false to serve only the first eligible candidate. provider.order alone is a preference and can leave other providers eligible.

provider.zdr: true restricts requests to routes with a tracked zero-data-retention guarantee. provider.min_privacy sets a hard floor: any, no_store, zdr, or confidential. The confidential tier requires verified provider compute, provider-side encryption, and explicit zero retention on the same route. If no eligible route remains, the request fails instead of downgrading.

This example pins OpenAI and requires the selected route to qualify for ZDR. It does not request confidential provider compute. Review the OpenAI route policy, including the distinction between managed credits and your own upstream account.

curl https://api.trustedrouter.com/v1/chat/completions \
  -H "Authorization: Bearer $TRUSTEDROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai/gpt-4o",
    "messages": [{"role": "user", "content": "Hello"}],
    "provider": {
      "only": ["openai"],
      "allow_fallbacks": false,
      "min_privacy": "zdr"
    }
  }'

For Europe-focused routing, the regional base URL is https://api-europe-west4.quillrouter.com/v1. It selects the gateway region. The trustedrouter/eu model alias selects an EU-focused provider pool; combine it with provider.only and provider.min_privacy for your approved routes. Gateway location alone is not an upstream data-residency guarantee. Keep strict residency requirements and the approved provider allowlist in your contract.

Batch has a different retention boundary

Batch is opt-in and retains encrypted artifacts scheduled for deletion after 30 days. Its storage boundary depends on GCP KMS, Cloud Storage, and the project's IAM administration. It does not have the same zero-retention property as ordinary inference.

Provider-native Batch can retain plaintext input for up to 26 hours and provider results for up to 6 hours. That execution path is blocked for ZDR, confidential, regional, and BYOK routes. Strict EU data-residency batch execution is not included. Review the DPA and obtain written approval of the applicable Batch boundary before using it for contractually restricted data.
