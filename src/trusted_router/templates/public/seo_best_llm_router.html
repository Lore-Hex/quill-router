Failover keeps your model. Model routing changes it.

Every AI router in this comparison gives you one API across many providers. The useful question is which decision it makes for you. Provider failover sends a request for the same model to another provider when one fails. Model routing sends it to a different model. Check which one a product does before relying on "automatic routing".

Routing

trustedrouter/auto

Tries a fixed list of recommended models across several providers, in order, and moves down the list when one fails. Privacy requirements filter the list before any provider is contacted.

Cost

trustedrouter/cheap

Tries low-priced chat models from several model makers, cheapest first. Each response reports usage.cost_microdollars, so you can check what every call cost.

Test it yourself: fallback, price and privacy

  1. Fallback: pick a model served by several providers on its model page. Send the same request with provider.only or provider.ignore and check which provider served each call. Read the failover guide for rollover behaviour.
  2. Price: send the same prompt through each route you are comparing and record usage.cost_microdollars. Compare real charges for your token mix against live pricing.
  3. Privacy: add "provider": {"min_privacy": "zdr"}, then exclude the qualifying providers. The request should fail before inference instead of taking a weaker route. The confidential endpoint returns 400 confidential_privacy_required when the setting is missing.

Choose managed or self-hosted by who will run it. A self-hosted proxy such as LiteLLM gives you full control of deployment and keys, and your team maintains it. A managed gateway removes that work; for sensitive data, check the privacy terms of the exact route, then run a small workload-specific evaluation before picking a default.
