How do you evaluate a multilingual local LLM?

Evaluate documents written naturally in each target language. Translated English benchmarks can miss regional terms, names and differences in formality.

2026-11-22

Evaluate a multilingual local LLM separately in every language you intend to support, starting with ten naturally written messages per language. Score meaning, tone and token use independently for each language.

Build a language-specific acceptance set

Ask a fluent reviewer to choose examples resembling real work: a support request, a scheduling change, a refusal, a technical explanation and a message mixing local language with product names. Include regional vocabulary and appropriate levels of formality. Keep personal data fictional so the same set can be used for an approved hosted comparison.

Write an expected meaning rather than one exact reference sentence. Several phrasings can be correct, while a polished answer can still reverse a negation or turn a tentative request into an instruction. Have the reviewer mark errors in names, quantities, dates, intent and register separately. These categories make disagreements actionable.

A model card's supported-language list is a useful starting filter. For example, Llama 3.3's card names English, German, French, Italian, Portuguese, Hindi, Spanish and Thai. Extend the evaluation with your audience's dialects, industry abbreviations and mixed-language conversations.

Fixture What to preserve What the reviewer checks
A local date format Day, month and uncertainty No unsupported date conversion
A mixed-language message Intent and product names No accidental translation of identifiers
A polite refusal Refusal and suitable tone No agreement added to sound helpful

Tokenizers make equal meaning take unequal space

Tokens are model-specific units that can represent words, parts of words or other text sequences. The research paper “Language Model Tokenizers Introduce Unfairness Between Languages” documents that equivalent translated content can require different token counts, affecting cost and usable context. Recount the same text when you change tokenizers.

Subword tokenizers represent frequent sequences with vocabulary entries and split other text into smaller units. The tokenizer's vocabulary and training data therefore matter alongside the writing system. Hugging Face's tokenizer documentation explains the encoding interface; use the actual tokenizer rather than an English words-to-tokens shortcut. Count Japanese, Arabic and Hindi requests separately from English requests.

Consider an illustrative paired-message test. Suppose one language averages 400 input tokens and another averages 700 for the same task under the chosen tokenizer. The ratio is 700 ÷ 400 = 1.75. Across 1,000 requests, that is 400,000 versus 700,000 input tokens, a 300,000-token difference.

The same difference consumes context. With 6,000 tokens available for evidence, 400-token passages allow 15 passages; 700-token passages allow eight complete passages. Keep instructions and answer space outside that allowance. A language can require a different chunking policy even when the model and application are otherwise identical.

Count your full prompt and preserve the output language

For an installed Transformers tokenizer, save your approved messages as UTF-8 files and run this Python sketch. Replace the directory with the exact tokenizer snapshot used by your local deployment. It loads local files and keeps the message text on your machine.

from pathlib import Path
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(
    "./approved-tokenizer", local_files_only=True
)
for path in sorted(Path("fixtures").glob("*.txt")):
    text = path.read_text(encoding="utf-8")
    content_tokens = tokenizer.encode(text, add_special_tokens=False)
    chat_tokens = tokenizer.apply_chat_template(
        [{"role": "user", "content": text}],
        tokenize=True,
        add_generation_prompt=True,
        return_dict=False,
    )
    print(path.name, len(content_tokens), len(chat_tokens))

The first count isolates message content. The second includes the tokenizer's chat formatting and the assistant-generation prefix. Add your real system message and tool definitions before using the count as a production budget. The installed tokenizer must include a compatible chat template.

Ask the model to respond in the user's language and preserve names, identifiers and quoted source text. Then test that instruction with mixed-language inputs. Do not automatically translate everything into English to reduce tokens: translation is another transformation whose errors and cost belong in the comparison.

Record generated tokens as well as input tokens. A model can answer correctly but switch languages, become unnecessarily verbose, or use an inappropriate level of formality. Those failures affect usability even when the input fits easily.

Try it on your workload

For each target language, select ten natural messages with a fluent reviewer. Include a local date, a mixed-language sentence and a domain-specific abbreviation. Add matched translations of three messages as a separate tokenization probe, keeping the natural messages as the main quality test.

Run the same task instruction and output requirements for each candidate. Save model revision, tokenizer revision, input and output counts, elapsed seconds and the untouched answer. Have reviewers score meaning and tone without seeing which model produced the response. Record corrections they would need before sending the answer to a customer.

Report results by language rather than pooling them. If nine of ten French answers pass and six of ten Hindi answers pass, the respective rates are 90% and 60%; an overall 75% conceals the difference that matters to users. These numbers illustrate the reporting format. Repeat failures with a corrected prompt to distinguish a fixable instruction problem from a persistent model weakness.

How to decide

Choose a model only for languages where it passes your factual and tone thresholds. Use per-language token budgets for context and cost planning. If one language remains weak, compare a different model for that language rather than increasing the context of a model that already received all the necessary information.
