How many people can share a local LLM?

Single-user tokens per second cannot predict queue delays when colleagues arrive together. Define acceptable wait time per user before sizing the server.

2026-11-22

Size a shared local LLM by completed jobs and waiting time at your busiest hour. Start with one, two and four simultaneous requests; keep the smallest configuration that meets your slowest acceptable response time.

Separate parallel requests from loaded models

A loaded model, an active request and a queued request consume different resources. Accepting more requests can improve hardware utilization, but active requests share the machine's memory bandwidth and compute. On one local GPU, agents share throughput and requests beyond active capacity wait in line.

The Ollama FAQ, checked on 2026-11-22, documents these controls:

Setting Purpose and current default
OLLAMA_NUM_PARALLEL Requests processed concurrently per model. Unset or zero lets MLX on Metal choose from memory and cache requirements; other backends default to 1.
OLLAMA_MAX_LOADED_MODELS Concurrent resident models, subject to memory: normally 3 × GPU count, or 3 for CPU inference.
OLLAMA_MAX_QUEUE Waiting requests before additional requests are rejected: default 512.

Ollama multiplies context allocation by parallelism: four requests at 4,096 tokens require 4 × 4,096 = 16,384 context tokens. When another model cannot fit, requests wait for memory. Start a dedicated terminal server with explicit settings after stopping an existing server:

OLLAMA_NUM_PARALLEL=2 OLLAMA_MAX_LOADED_MODELS=1 \
OLLAMA_MAX_QUEUE=16 OLLAMA_CONTEXT_LENGTH=4096 ollama serve

For the macOS app, set these variables with launchctl setenv and restart it. For a Linux systemd service, put Environment="NAME=value" entries under [Service] using systemctl edit ollama.service, then reload systemd and restart the service. Apply environment changes to the process that starts the service.

Give llama.cpp slots an explicit context budget

The current llama.cpp server reference lists --parallel as the slot count, defaulting to -1 for automatic selection. Continuous batching, controlled by --cont-batching and --no-cont-batching, is enabled by default as of November 2026. It lets the server schedule work from multiple requests together rather than reserving the entire decoding loop for one conversation.

llama-server --model /absolute/path/model.gguf \
  --host 127.0.0.1 --port 8080 \
  --parallel 4 --ctx-size 16384 --no-kv-unified --cont-batching

Use your downloaded model's real path and a model supporting at least 4,096 context tokens. With the separate sequence allocation selected here, the 16,384-token context is divided across four slots: 4,096 tokens per slot, including prompt and generation. Increasing slots without increasing the total context reduces that allowance. Check the startup allocation before sending long conversations.

Unified KV allocation changes this picture: current builds also support --kv-unified and --kv-unified-per-slot. Do not carry the simple division rule into a shared-pool configuration without checking its per-request limit. Pin your server build and configuration alongside benchmark results so the next upgrade does not silently change the experiment.

Use concurrency to finish the whole workload

Suppose eight agents each need 600 output tokens, and your measured single-request decode rate is 30 tokens per second. Ignoring prompt processing for this illustrative calculation, one request takes 600 / 30 = 20 seconds. Serial completion times are 20, 40, 60, 80, 100, 120, 140 and 160 seconds. Mean completion time is 90 seconds; the last agent waits 140 seconds before its own decoding starts.

If four concurrent slots still deliver only 30 output tokens per second in aggregate, each equal-length request receives roughly 7.5 tokens per second. Two waves finish around 80 and 160 seconds. The total decoding work still takes 160 seconds. If batching raises measured aggregate throughput to 60, the 4,800-token workload instead needs about 80 seconds. Add prompt-processing time to each scenario.

For sustained many-user serving, evaluate vLLM. Its documented PagedAttention memory management, continuous batching, chunked prefill and distributed serving make it a relevant higher-concurrency option. Choose it when you can operate a serving stack and have enough recurring traffic to justify that effort. A runtime change still needs the same acceptance test as a GPU purchase.

Try it on your workload

Prepare 24 fixed prompts: 16 ordinary requests and eight long ones resembling your real workload. Keep model, quantization, output limit and prompt text fixed. Replay the set at one, two and four simultaneous sessions, warming the model once before each measured run. Record submission time, first output time, completion time, input and output token counts, errors and accepted answers.

Report completed jobs per minute and the slowest request, plus the 95th percentile when your sample is large enough to make it useful. Count queued time inside user waiting time. Repeat with short requests arriving while long ones are active: a batch that finishes quickly can still make interactive users wait too long.

Then replay an approved fictional set through a hosted endpoint with the same client concurrency. Increase concurrency gradually and keep retries bounded. Compare total completion time and accepted answers, not just a stream's fastest interval. Save the exact runner version and configuration with the result.

How to decide

  • Keep one local machine when it meets busy-period waiting targets with memory headroom.
  • Raise parallelism only while accepted jobs per minute improve without unacceptable individual waits.
  • For short bursts, compare hosted overflow with the cost of equipment that sits idle between bursts.

Run eight coding agents together for less than a cent

Eight coding agents working at once on qwen/qwen3-coder-30b-a3b-instruct cost about 0.44 cents in tokens on TrustedRouter for the worked example. On 2026-11-22, the live catalog listed approximately $0.132 per million input and $0.475 per million output tokens. Eight requests with 2,000 input and 600 output tokens each use 16,000 input and 4,800 output tokens. Cost = 0.016 × $0.132 + 0.0048 × $0.475 = $0.004392, about 0.44 cents.

On one local GPU, the agents share throughput, and requests beyond its parallel capacity wait in line; through a per-token API, independent requests can run at the same time for the same token bill as running them sequentially. Assign separate repository tasks to each agent and retain the same acceptance checks. Dependencies between steps still determine which requests are ready to submit.

Prices change; check the model catalog, follow agent setup and review private API routing for approved code. Keep local execution for offline data or steady work your existing hardware handles comfortably.
